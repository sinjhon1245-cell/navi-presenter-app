# 수업 안정성: 여러 PC · 수업 중 PIN · 교사별 기록 · PC 끊김

전체 기능 점검에서 재현된 문제를 고친 기록이에요. 시험은 `tests/control.spec.js`(실제 브라우저 여러 개 + Firebase 에뮬레이터)예요.
**보안 규칙은 바꾸지 않았어요.** 기존 칸(`hub.pc` · `on` · `run` · `startReq` · `startAck`)과 Firestore 거래(transaction)만 써요.

## 1. 재현된 문제

| 재현 | 원인 |
|---|---|
| 두 번째 PC를 열면 PIN 휴대폰이 끊겨요 | PC가 열릴 때마다 `run`을 새로 만들었어요 |
| 두 번째 PC가 계정의 수업 내용을 덮어써요 | 페이지가 자기 최근 수업을 다시 열며 `lessons/deck`에 썼어요 |
| 두 번째 창의 ‘기록 없이 버리기’가 진행 중인 수업을 지워요 | 누가 수업을 맡았는지 아무도 확인하지 않았어요 |
| 수업 중 ‘PIN 바꾸기’를 누르면 수업이 사라져요 | PIN이 바뀌면 세션 문서가 바뀌는데, 막는 곳이 없었어요 |
| 공용 PC에서 앞 교사의 기록이 보여요 | 브라우저 저장소가 계정과 상관없이 하나였어요 |
| PC가 꺼진 채 휴대폰으로 끝내면 기록이 없어요 | 휴대폰이 세션에 ‘끝남’을 바로 썼고, 기록은 PC만 쓸 수 있어요 |

## 2. 누가 수업을 맡는가

수업을 맡는 것은 **PC 창 하나**예요. `lessons/hub.pc`가 그 창을 가리켜요. 값은 `{브라우저 id}-{창 id}`예요.
브라우저 id는 localStorage(`navi-browser`), 창 id는 sessionStorage(`navi-tab`)에 있어서 새로고침해도 같은 창이고, 새 창이나 다른 PC는 달라요.

각 PC 창의 상태(`ctl`):

| 상태 | 뜻 | 서버에 쓰나요 |
|---|---|---|
| `mine` | 이 창이 맡고 있어요 | 네. 쓸 때마다 거래로 확인해요 |
| `free` | 맡은 PC가 없어요(`hub.on` false, 또는 이 브라우저에서 사라진 창) | 교사가 행동하면 먼저 맡아요 |
| `other` | 다른 창이나 PC가 맡고 있어요 | 아니요. 이 화면에만 남아요 |

**페이지를 열거나 로그인하는 것만으로는 아무것도 쓰지 않아요.** `run` · `hub` · `deck` · `session` · `settings` 모두 그대로예요.
PC가 수업을 맡는 때는 교사의 행동이 있을 때뿐이에요: 수업 고르기 · 고치기, 학생 화면 열기, 휴대폰 연결 · QR 보기, 수업 시작.
휴대폰이 지금 PC를 찾고 있을 때(`ping`, 맡은 PC가 없을 때)도 그 PC가 답해요. 처음 쓰는 계정은 PIN을 계정에 저장하려고 한 번 맡아요.

### 거래

- `db.claim`: hub를 읽어 맡을 수 있을 때만 `pc`를 바꿔요. 조용히 맡을 때는 다른 PC가 켜져 있거나(`held`) 수업이 진행 중이면(`live`) 거절해요.
  이어받기는 화면에서 본 그 PC에서만 받아요(`moved`). 두 PC가 같은 순간 눌러도 한쪽만 돼요. `run`은 있던 값을 그대로 둬요.
- `db.held`: 맡은 창의 쓰기. hub를 읽고 `pc`가 이 창일 때만 한 번에 적용해요. 그 사이 hub가 바뀌면 Firestore가 거래를 다시 돌려요.

PC의 수업 · 수업 내용 · 설정 · 준비 상태 쓰기는 모두 `sendOwn` → `ownPump` → `db.held`로 가요. 순서대로 하나씩 보내요.
**끊긴 동안 쓴 것은 Firestore 오프라인 대기열이 아니라 화면 쪽 대기열(`ownQ`)에 있어요.** 그래서 끊긴 사이 다른 PC가 이어받았다면,
다시 이어졌을 때 거래가 `lost`로 거절되고 그 쓰기는 버려져요. 예전 방식이면 오래된 쓰기가 나중에 서버에 닿아 수업을 되돌렸을 거예요.

### 다른 기기에서 보이는 것

‘다른 기기에서 수업을 진행하고 있어요.’와 세 가지 선택:

- **현재 수업 확인하기**: 읽기 전용 화면(`viewWatch`). 수업을 바꿀 단추가 없어요.
- **이 기기에서 이어서 진행하기**: 확인 줄 뒤 거래로 이어받아요. 장면 · 신호등 · `run` · PIN 휴대폰은 그대로 이어지고, 앞 PC는 읽기 전용이 돼요.
  앞 PC의 학생 창은 ‘다른 기기에서 수업을 진행하고 있어요’로 바뀌어요. 이어받은 뒤의 기록은 이어받은 PC에 남아요.
- **새 수업 준비하기**: 진행 중인 수업은 건드리지 않고 이 브라우저에서만 준비해요. 그 수업이 끝나야 시작할 수 있어요.

수업이 없고 다른 PC가 준비만 하고 있으면 ‘다른 기기에서 수업을 준비하고 있어요.’와 이어서 준비하기를 보여 줘요.
여기서 ‘수업 시작’을 누르면 확인 줄 뒤에 시작해요.

‘기록 없이 버리기’와 ‘기록 저장하고 끝내기’는 **이 브라우저의 수업 사본이 있고, 다른 PC가 맡고 있지 않을 때만** 보여요. 실제로 버릴 때도 거래로 맡은 뒤에만 서버를 바꿔요.

같은 브라우저에서 닫힌 창은 `BroadcastChannel`로 살아 있는 창을 확인해 구별해요. 창을 강제로 닫아 ‘닫힘’ 소식이 서버에 못 가도(`on`이 true로 남아도) 다시 열면 ‘다른 기기’가 아니라 이 브라우저의 끝나지 않은 수업으로 나와요.

## 3. 수업 중 PIN

- 수업 중에는 ‘PIN 바꾸기’가 막혀 있고 까닭을 말해요. 수업을 맡지 않은 PC도 바꾸지 못해요.
- 새 PIN은 늘 지금 PIN과 달라요(2026-11-12, PR #13 CI에서 찾음): 무작위로 고를 때 지금 PIN을 빼지 않아 ‘PIN 바꾸기’가 가끔(실제 1만 번에 1번, 시험 구간에서는 40번에 1번) 같은 PIN을 다시 뽑았어요. 다른 반이 쓰는 PIN을 피할 때도 같아요(`newPin(not)`). 시험: `connect.spec.js` ‘PIN 바꾸기는 늘 지금과 다른 PIN으로’(고를 수 있는 PIN 2개로 좁혀 8번).
- 바꿀 때는 먼저 거래로 묻고(이 창이 맡았는지, 그 PIN의 수업이 진행 중인지), 된 뒤에만 화면의 PIN을 바꿔요.
- 지난 PIN의 세션 문서와 기록은 그대로예요. `run`은 PIN으로 연결한 휴대폰이 있을 때만 바뀌어요(그 휴대폰을 끝내려고요).
- 페이지가 처음 만든 임시 PIN이 계정의 PIN으로 바뀌는 것은 ‘PIN 변경’으로 치지 않아요(`pinSure`). 예전에는 이때 휴대폰이 끊길 수 있었어요.

## 4. 교사별 로컬 기록

| 무엇 | 로그인한 교사 | 로그인하지 않음 |
|---|---|---|
| 기록 · 최근 수업(IndexedDB) | `navi-local-{교사 id}` | `navi-local` |
| 진행 중 수업 사본(localStorage) | `navi-run-{교사 id}`, `navi-run-done-{교사 id}` | `navi-run`, `navi-run-done` |

- 로그아웃하면 그 교사의 기록은 보이지 않고, 다른 계정에도 보이지 않아요. 다시 로그인하면 그대로 있어요.
- 예전 기록(`navi-local`)은 **지우지도 옮기지도 않았어요.** 로그인하지 않은 화면에 그대로 보여요.
- 로그인한 교사의 수업 기록 화면은 몇 건 있는지만 말해요. ‘이 계정으로 가져오기’(확인 줄 뒤)를 누르면 사본을 계정 저장소에 넣고,
  원본에는 `claimedBy`만 적어요. 그러면 다른 계정과 로그인하지 않은 화면에서는 숨고, 원본은 남아요. ‘가져오기 되돌리기’로 원래대로 돌아가요.
- 이것은 화면 분리예요. 암호화가 아니라서 브라우저 개발자 도구로는 읽을 수 있어요. 공용 PC의 기록을 완전히 지키는 것은 기록을 계정에 두는 1단계-2에서 해요.

## 5. 휴대폰에서 시작하기 · 끝내기

시작과 끝내기는 **늘 PC가 해요.** 학생 창과 기록이 PC에 있기 때문이에요. 휴대폰은 세션에 ‘시작’이나 ‘끝남’을 쓰지 않아요.
두 요청은 같은 절차를 따르고, 같은 칸(`hub.startReq` · `hub.startAck`)을 써서 보안 규칙은 그대로예요.

| 단계 | 시작 | 끝내기 | 누가 · 무엇을 |
|---|---|---|---|
| 1. 묻기 | `sta-{수업 지문}-{k}` | `end-{수업 시작}-{k}` | 휴대폰이 요청을 남겨요. 시작은 휴대폰이 본 수업(제목 · 장면 수)의 지문을 담아요 |
| 2. 승인 | `startAck` ok | `startAck` ok | PC가 할 수 있는지 보고 답해요. 아직 아무것도 하지 않아요(`reqPend`) |
| 3. 실행 | `go-{k}` | `fin-{수업 시작}-{k}` | 그때도 기다리던 휴대폰만 보내요 |
| 4. 확정 | | | PC가 거래(`db.held` + `req` + `until`)로 요청을 지우며 답을 쓰고, 그 거래가 된 뒤에만 시작하거나 끝내요 |

- **요청 ID**: 단계마다 id가 달라요. PC는 한 번 본 id를 다시 보지 않고(`hubDone`), 실행은 자기가 막 승인한 것(`reqPend`, 4초 안)만 받아요. 승인 없이 온 실행 · 모르는 id · 10초 넘은 요청은 받지 않아요(`late`).
- **취소**: 휴대폰은 4초 안에 답이 없으면 거래(`db.settle`)로 정리해요. 요청이 아직 있으면 지우고, PC의 답이 먼저 와 있으면 그 답을 받아요. 서버의 지금 상태(`hub.live`)도 함께 봐요.
  그래서 PC의 확정과 휴대폰의 취소는 **둘 중 하나만** 일어나요.
- **‘응답 없음’은 확인된 때만**: 휴대폰이 ‘교사 PC가 응답하지 않아요’ · ‘교사 PC를 다시 연결한 후 수업을 종료해 주세요’라고 단정하는 것은, 서버가 요청을 지웠다고 확인했을 때(그 뒤로 PC는 실행할 수 없어요)나 묻기 단계였을 때(그 단계만으로는 아무것도 실행되지 않아요)뿐이에요.
  실행 단계에서 서버에 닿지 못하면 ‘휴대폰 인터넷이 불안정해 … 확인하지 못했어요. 다시 연결되면 지금 상태로 맞춰져요’라고 말하고, 나중에 온 답이나 수업 소식을 그대로 따라가요.
- **응답만 잃은 승인**: PC의 승인 거래가 서버에 닿았는데 응답만 잃어 다시 시도되면, 지운 요청 대신 자기가 쓴 승인이 서버에 있어요. 그때는 된 것으로 보고 시작 · 끝내기를 한 번 이어서 해요(다시 쓰지 않아요).
- **승인 마감**: PC는 실행 요청을 본 뒤 4초(자기 시계) 안에만 승인 거래를 시도해요(아직 서버에 쓰지 않은 거래).
- **실행 직전 다시 확인**: 승인 거래가 끝난 순간에 그 요청이 아직 맞는지 다시 봐요. 끝내기는 요청 id에 든 수업(t0)이 지금 수업일 때만, 시작은 진행 중인 수업 · 미리보기가 없고 PC의 수업이 요청의 지문과 같을 때만 해요.
  그래서 응답을 잃은 승인이 한참 늦게 다시 시도돼도, 그 사이 교사가 시작한 다음 수업이나 미리보기는 건드리지 않아요.
  그때 실행하지 못하면 PC가 정정 답(`startAck` ok false와 까닭)을 써서, 휴대폰은 ‘시작 요청을 받았어요’에서 멈추지 않고 까닭을 말해요.
- **휴대폰이 본 수업만 시작**: 묻기 · 실행 · 실행 직전 모두 지문을 맞춰 봐요. 그 사이 교사가 PC에서 다른 수업을 고르면 시작하지 않고 ‘PC의 수업이 바뀌었어요’라고 말해요.
- **확인하지 못한 요청은 다시 확인**: 휴대폰은 ‘확인하지 못했어요’ 상태의 요청을, 서버에 닿을 때 5초마다 다시 정리해요. 결과를 알게 되면 그대로 말하고, 그 수업이 끝났거나 다른 수업이면 안내를 지워요.
- **늦게 실행되지 않는 까닭**: 휴대폰이 포기한 뒤 PC가 돌아와 낡은 요청을 봐도, PC는 ‘묻기’에 답할 뿐이에요. 포기한 휴대폰은 실행 단계를 보내지 않아요.
  취소가 서버에 닿지 못해 낡은 요청이 남아 있어도 마찬가지예요. 시각을 기기끼리 비교하지 않아서 시계 차이에 흔들리지 않아요.
- **실제로 시작됐을 때**: PC의 승인을 받았거나 서버가 수업 중이라고 하면, 소식이 늦어도 휴대폰은 실패라고 말하지 않아요.
  6초가 지나도 소식이 없으면 ‘PC가 시작 요청을 받았어요. 이 휴대폰에 수업 소식이 오기를 기다려요.’라고만 말해요(PC가 받았다는 사실만).
- **연속 탭 · 중복**: 보내는 동안 단추가 잠기고 요청은 하나만 나가요. PC와 휴대폰이 같은 순간 시작해도, 같은 실행 요청이 다시 와도 수업은 한 번만 시작돼요(`live`).
- **제어권 이전**: 요청은 그때 맡은 PC 창 앞으로 가요(`pc`). 승인한 PC가 그 사이 넘겨주면 그 PC는 받지 않고, 새 PC는 승인한 적이 없어 받지 않아요. 휴대폰에서 다시 누르면 새 PC가 시작해요.

끝내기에서 4초 안에 답이 없으면 수업은 그대로이고, 휴대폰은 ‘교사 PC와 연결되어 있지 않아요. 교사 PC를 다시 연결한 후 수업을 종료해 주세요.’라고 말해요.
PC가 다시 이어지면 그대로 이어서 하고, PC를 닫았다 열면 ‘끝나지 않은 수업’에서 이어서 하기 · 기록 저장하고 끝내기를 골라요. 기록 id는 수업 시작 시각으로 만들어 두 번 생기지 않아요.

## 6. 보안 영향

- 규칙 파일을 바꾸지 않아서 배포된 규칙(`d82d18285c724423`)과 같아요. 넓어지는 권한이 없어요.
- PIN 휴대폰이 쓰는 칸도 그대로예요(`startReq` · `ping` · `cmds`). 끝내기 요청은 시작 요청과 같은 칸이고, 실제로 끝내는 것은 교사 PC예요.
- **달라진 점 하나**: 예전에는 PC가 새로 열리면 `run`이 바뀌어 PIN 휴대폰이 끊겼어요. 이제는 열기만으로는 끊기지 않아요(교사가 요청한 동작).
  그래서 수업 전에 허용한 휴대폰은 PC를 강제로 닫았다 열어도 수업이 끝나거나, PIN을 바꾸거나, 연결을 끊거나, 3시간이 지날 때까지 남아요. 허용은 그 교사가 한 것이고 수업이 끝나면 전과 같이 끊겨요.
  `firestore.rules`의 주석 한 줄은 이 옛 동작을 말해요. 배포본과 파일이 같도록 이번에는 고치지 않았고, 다음 규칙 배포 때 함께 고쳐요.
- 같은 계정의 창은 규칙이 구별하지 못해요(UID가 같아요). 그래서 이 잠금은 **사고를 막는 장치**이고 공격을 막는 장치가 아니에요. 계정 주인이 일부러 코드를 고쳐 쓰는 경우는 막지 않아요.

## 7. 남은 것

- PC가 승인 거래를 마친 바로 뒤, 수업을 쓰기 전에 꺼지면 휴대폰은 ‘PC가 시작 요청을 받았어요’에서 기다려요. 거의 일어나지 않고, 다시 누르면 새 요청으로 시작해요.
- 아주 느린 망에서는 휴대폰 시작이 ‘요청이 늦게 닿았어요’로 실패할 수 있어요. 늦게 시작되는 쪽이 아니라 시작하지 않는 쪽이에요. 요청마다 휴대폰 0.7초 · PC 0.3초를 늦춰도 정상 시작했어요(약 5.4초).
- 휴대폰과 PC가 함께 끊긴 채 승인이 늦게 닿으면, 휴대폰이 ‘확인하지 못했어요’라고 말한 뒤 수업이 시작될 수 있어요. 단정하지 않았고, 다시 이어지면 그 수업을 보여 줘요.
- 창을 닫을 때의 ‘닫힘’ 소식은 서버에 못 갈 수 있어요. 그러면 다른 PC에는 진행 중으로 보이고, 이어받기로 해결해요. 휴대폰 끝내기는 4초 뒤 안내해요.
- 인터넷이 끊긴 채 수업을 맡지 않은 PC에서는 수업을 시작할 수 없어요(서버에 확인할 수 없어서). 맡고 있던 PC는 끊겨도 계속 수업해요.
- 구글 로그인 휴대폰은 PC가 없어도 장면을 넘길 수 있어요(예전과 같아요).
- 다음 단계: 학생 화면 영상 재시작, 미리보기 노출, 한 화면 수업의 끝내기 단추.

## 8. 재현과 시험

모두 `tests/control.spec.js`에서 실제 브라우저 여러 개와 Firebase 에뮬레이터로 돌려요. 문서가 그대로인지는 관리자 권한으로 `updateTime`까지 비교해요.

| 요청한 상황 | 시험 | 확인한 것 |
|---|---|---|
| PC A 수업 중 PC B 접속 | PC A 수업 중 PC B 접속 | 네 문서가 `updateTime`까지 같아요. B가 쓴 횟수 0 |
| PC B 접속 중 PC A 조작 | 같은 시험 | A의 넘기기 · PIN 휴대폰 명령이 그대로 가고 B는 읽기만 해요 |
| PC B에서 제어권 이전 | PC B에서 제어권 이전 · 두 PC가 같은 순간 이어받기 | 확인 줄 뒤에만 넘어가요. `run` 그대로. 동시에 누르면 한쪽만 돼요 |
| 다른 PC의 기록 없이 버리기 | 다른 PC의 ‘기록 없이 버리기’ | 같은 브라우저의 둘째 창에도 단추가 없어요. 코드로 해도 `lost` |
| 수업 중 PIN 변경 시도 | 수업 중 PIN 바꾸기 · 다른 PC에서는 PIN을 바꿀 수 없어요 | 단추가 막혀 있고 서버 거래도 `live`로 거절해요. 끝난 뒤에는 바뀌어요 |
| PIN 휴대폰 연결 유지 | 수업 전 PIN 휴대폰 · PC A 수업 중 PC B 접속 | 수업 전 · 중 모두 끊기지 않아요 |
| 교사 A 로그아웃 후 교사 B 로그인 | 공용 PC · 예전 로컬 기록 | 서로 보이지 않고, 예전 기록은 지우지 않아요. 가져오기 · 되돌리기 |
| PC 끊김 → 복구 → 정상 종료 | PC 끊김 → 끝내기 → 복구 · PC를 닫은 뒤 끝내기 · 안내가 뜬 뒤 PC가 돌아와도 · PIN 휴대폰도 같아요 | 끊긴 동안 끝나지 않아요. 기록은 한 번만 |

그 밖에 더 넣은 시험: 끊긴 PC의 오래된 쓰기가 이어받은 수업을 되돌리지 않아요. 같은 창 새로고침 · 강제 종료는 ‘다른 기기’가 아니에요. 다른 PC의 수업이 진행 중이면 시작하지 못해요. PIN 휴대폰의 빠른 연속 넘기기.

### 휴대폰 수업 시작 요청(2026-11-07 추가)

| 상황 | 시험 | 확인한 것 |
|---|---|---|
| 시간 초과 뒤 PC 복구 | 수업 시작 시간 초과 | 취소가 닿았을 때도, 휴대폰의 쓰기를 막아 낡은 요청이 남았을 때도 PC가 돌아와 시작하지 않아요. PC는 낡은 요청에 답만 하고 지워요 |
| 승인 뒤 소식이 늦음 | 실제로 시작됐으면 | PC의 수업 쓰기를 9초 늦춰도 휴대폰에 실패 안내가 한 번도 없고, ‘PC가 시작 요청을 받았어요’ 뒤 수업으로 이어져요 |
| 승인이 취소보다 늦음 | 취소보다 늦으면 | PC의 확정 쓰기를 5.5초 늦추면 휴대폰의 취소가 먼저예요. PC는 시작하지 않고, 휴대폰은 시작되지 않았다고 말해요 |
| 확정과 취소가 겹침 | 취소와 승인이 겹쳐도 | 실행 요청 뒤 0–900ms에 취소를 보내요. 매번 ‘휴대폰이 받은 답’과 ‘서버의 수업’이 같아요 |
| 위조 · 중복 요청 | 위조 · 중복 요청 | 승인 없는 실행과 모르는 id는 `late`, 시작 뒤의 같은 요청 · 새 요청은 수업을 다시 시작하지 않아요(t0 그대로) |
| 연속 탭 · PC와 동시 시작 | 연속 탭 | 세 번 눌러도 요청은 하나예요. PC와 휴대폰이 같은 순간 시작해도 수업은 하나예요. 다음 수업도 다시 시작돼요 |
| 제어권 이전 | 제어권이 넘어가는 중 · 낡은 시작 요청 | 앞 PC가 승인한 요청은 앞 PC도 새 PC도 실행하지 않아요(새 PC가 학생 창까지 준비해도 `late`) |
| 끝내기도 같은 절차 | 끝내기도 같아요 | PC의 확정이 늦으면 끝나지 않고 기록도 없어요. 다시 누르면 기록은 하나예요 |
| 승인의 응답만 사라짐 | 응답만 사라져도(시작 · 끝내기) | 승인 쓰기는 서버에 보내고 응답만 끊어요. 다시 시도한 PC가 시작 · 끝내기를 한 번 이어서 해요. 기록 하나 |
| 승인이 늦고 휴대폰도 끊김 | 늦게 닿고 휴대폰도 끊기면 | 휴대폰은 ‘응답 없음’이라 단정하지 않고, 승인이 닿아 시작된 수업을 그대로 보여 줘요 |
| 승인 마감 | 승인 거래의 마감 | 마감이 지난 승인 거래는 거절되고 아무것도 쓰지 않아요 |

| 늦게 다시 시도된 끝내기 승인 | 한참 늦게 다시 시도돼도 | 승인 응답을 잃고, 다시 시도를 붙잡아 둔 사이 교사가 수업을 끝내고 다음 수업을 시작해요. 놓아줘도 다음 수업은 끝나지 않고 기록은 하나예요 |
| 확인하지 못한 실행 요청 | 확인하지 못한 실행 요청 | 휴대폰이 10초 넘게 쓰지 못한 뒤 다시 되면, 남은 요청을 스스로 정리하고 ‘응답 없음’을 정확히 말해요 |

| 시작 요청 중 다른 수업 선택 | 다른 수업을 고르면 | 앞 수업을 보고 승인받은 실행은 `moved`로 받지 않아요. 휴대폰은 바뀐 수업을 보여 주고, 다시 누르면 그 수업으로 시작해요 |
| 승인 직후 미리보기 | 미리보기를 누르면 | PC는 시작하지 않고 정정 답을 써요. 휴대폰은 ‘수업 미리보기’ 까닭을 말해요 |

마지막 일곱 줄은 병합 전 별도 검토(세 번)가 찾은 경우예요. 고치기 전 코드에서 이 시험들이 실패하는 것을 먼저 확인했어요.
아티팩트 런타임(`db.settle`이 없는 곳)에서는 휴대폰이 예전처럼 한 번 포기하고 요청을 지워요. 주기적으로 다시 쓰지 않아요.

부하 시험: 위 시험과 빠른 연속 넘기기를 6개씩 동시에 3번 반복해 30번 모두 통과했어요.
겹침 시험에서는 취소로 끝난 경우(0–15ms)와 시작된 경우(0–25ms)가 모두 나왔고, 휴대폰과 서버가 어긋난 적은 없어요.

작업 중 시험이 찾아낸 문제 세 가지(모두 고쳤어요):

- **안내 뒤에 수업이 끝나는 문제**: 휴대폰이 ‘연결 안 됨’이라고 말한 직후 PC가 돌아오면 지워지기 전의 요청으로 수업이 끝났어요. 두 단계 끝내기로 고쳤어요.
- **이어서 하기가 휴대폰의 넘기기를 덮는 문제**: 이어서 하기가 서버와 같은 수업을 통째로 다시 썼어요. 서버가 최신이면 쓰지 않아요.
- **PIN 휴대폰의 둘째 탭이 거절되는 문제**: PC는 ‘휴대폰이 본 뒤로 다른 일이 없었는지’를 한 단계만 기억했어요. 쓰기가 조금 느려지자 부하가 있을 때 8번 중 5번 재현됐어요. 그 휴대폰 명령의 단계를 모두 기억해서, 18회 연속 넘기기 × 8개 동시 실행이 모두 통과해요.
