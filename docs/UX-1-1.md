## 1. 지금 화면의 문제 (실제 연결 상태로 찍은 사진 기준)

| 화면 | 문제 |
| --- | --- |
| PC 준비 | 휴대폰 연결이 ‘발표 설정’ 탭 안 ‘QR · PIN 보기’ 단추 뒤에 숨어 있어요(세 번 눌러야 QR). ‘시작 전 확인’ 세 가지가 한 줄 작은 글씨라 준비됐는지 한눈에 안 보여요. 왼쪽 메뉴 아래 상태와 같은 내용을 두 번 말해요 |

| 휴대폰 대기 | 한 줄 글뿐이에요. 어떤 수업인지, PC · 학생 화면이 준비됐는지, 무엇을 할 수 있는지 없어요 |

## 2. 고친 화면 구조 (한 화면 = 가장 중요한 행동 하나)

| 화면 | 위(상태) | 가운데(내용) | 강조할 행동 하나 |
| --- | --- | --- | --- |
| PC 준비 | 수업 제목 · 저장 위치 · **준비 세 칸(발화 · 학생 화면 · 휴대폰)** | 장면 목록 · 장면 편집 · 수업 자료 | **수업 시작**. ‘휴대폰 연결’은 머리의 보조 단추 → 연결 창(QR · PIN) |
| PC 연결 창 | 연결 방식 두 가지 | 왼쪽 QR(구글 계정 · PIN 둘 다), 오른쪽 휴대폰 연결 PIN 4자리(3분 · 9절) · 연결 요청 목록 | 요청이 오면 **허용** |
| PC 수업 진행 | 수업 이름 · 진행 막대 · 시계 · **상태 한 칩(진행 중 · 연결 끊김)** · 학생 화면 · 도구 · 더보기 | 핵심 발화(가장 큼) · 학생 화면 · 다음 장면 | **다음**. 신호등은 테두리만 있는 조용한 묶음 |
| 휴대폰 연결 | 수업 내비 | 두 방식: **구글 계정으로 연결**(다음부터 자동) / PIN으로 연결 | 구글 계정으로 연결 |
| 휴대폰 대기 | 상태 칩(준비 완료 · 확인 중 · PC 응답 없음) | 수업 제목 · 준비 세 줄(교사 PC · 수업 자료 · 학생 화면) | **수업 시작**(준비가 다 됐을 때만, 확인 한 번 더) |
| 휴대폰 진행 | 상태 칩 · 장면 n/전체 · 수업 시계 | 장면 이름 · **핵심 발화(가장 큼)** · 개념 · 메모 | **다음**(엄지 자리 가장 큼) · 이전. 신호등은 한 줄 작은 묶음, 목차 · 자료는 같은 높이 |

### 공통 규칙 (docs/DESIGN-SYSTEM.md에 반영)
- **상태 칩 하나**로 말해요: 확인 중(빈 점) · 준비 완료/연결됨(채운 점) · 수업 진행 중(강조색 점) · 연결 끊김(주황). 신호등 색은 상태에 쓰지 않아요.
- 단추 높이 세 가지: 작게 36 · 보통 44 · 엄지 56(휴대폰 넘기기 64). 아이콘 18px + 글자, 왼쪽 정렬 묶음은 8px 간격.
- 칸 나눔은 선과 여백. 테두리 상자는 ‘집어 드는 것’(슬라이드 · 연결 창 · 확인 줄)에만.
- 작은 보조 문구는 화면마다 꼭 필요한 한 줄만.

## 3. 휴대폰 연결 두 가지

### 3-1. 구글 계정으로 연결 (지금 되는 것을 더 자동으로)
- 처음 한 번 로그인하면 Firebase가 이 휴대폰 브라우저에 로그인을 남겨요. 다음에 QR을 찍으면 **로그인 화면 없이 바로** 그 계정의 지금 수업으로 가요.
- QR 안의 PIN이 예전 것이어도(PC가 PIN을 바꿨어도) 같은 계정이면 **그 계정의 지금 수업**을 따라가요. 다른 계정이면 그 계정 이메일을 보여 주고 ‘다른 계정으로 로그인’을 줘요.

### 3-2. 연결 코드로 연결 (구글 로그인 없이, 휴대폰 연결 코드 6자리) — Spark 무료로 되는 구조, **실제 적용은 교사 승인 뒤** · 2차 보완은 8절
> **3차(9절)에서 6자리 연결 코드를 없애고 수업 PIN 4자리 하나로 바꿨어요.** 아래 표는 2차까지의 설계 기록이에요. 지금 쓰는 것은 9절이에요.

보안 규칙은 지금처럼 교사 UID만 열어 두고, PIN만으로는 아무것도 열리지 않아요. 휴대폰은 **교사 PC가 허용한 그 휴대폰 한 대만, 정해진 시간 동안, 그 수업만** 읽고 넘길 수 있어요.

| 단계 | 누가 | 무엇을 | 보안 |
| --- | --- | --- | --- |
| 1 | 교사 PC(구글) | ‘PIN으로 연결’을 열면 6자리 코드 문서 `pairs/{코드}` = {교사, 수업, 5분 뒤 만료, 열림, 요청 수 0} | 코드 문서는 교사만 만들고 닫아요 |
| 2 | 휴대폰 | 익명 로그인(Firebase Anonymous Auth, 무료) → 코드 입력 → `pairs/{코드}/asks/{휴대폰 id}` 요청 하나 | 코드가 열려 있고 만료 전일 때만. 코드마다 요청 3개까지(규칙이 요청 수를 함께 올려야만 허락) |
| 3 | 교사 PC | ‘휴대폰 1대가 연결을 요청해요 · 허용 / 거절’ | **PC가 허용해야만** 열려요. 코드를 맞혀도 PC가 모르는 요청은 거절 |
| 4 | 교사 PC | 허용하면 `teachers/{교사}/devices/{휴대폰 id}` = {수업 번호, 이번 수업 run, 3시간 뒤 만료} 하나, 코드는 닫음(한 번만) | 규칙: 이 문서가 있고 · 만료 전이고 · 익명 로그인이고 · run이 PC의 지금 수업일 때만 그 수업 · 수업 내용 읽기. 수업 문서는 못 쓰고 명령만 남겨요(8절) |
| 5 | 교사 PC | 수업을 끝내거나 ‘연결 끊기’를 누르면 그 기기 문서를 지워요 | 끝나면 바로 권한이 사라지고, 잊어도 3시간 뒤 만료 |

- 추가 서비스: **Firebase 익명 로그인 켜기**(무료, Spark 그대로) 하나. 서버 함수(Cloud Functions, Blaze 필요)는 쓰지 않아요.
- 규칙 변경은 ‘허용된 기기에만’ 여는 것이라 권한을 넓히는 변경이에요 → `CLAUDE.md`대로 **실행 전에 교사 승인**. 이 브랜치에서는 에뮬레이터로만 만들고 시험해요.
- 남는 한계: 요청 수 제한은 코드 하나당이라, 공격자가 코드를 바꿔 가며 시도할 수는 있어요(6자리 100만 가지 · 5분 만료 · PC 허용이 필요해서 실제로 들어올 수는 없어요).

## 4. 휴대폰에서 수업 시작

- PC는 상태가 바뀔 때만(주기적으로 쓰지 않음) `teachers/{교사}/lessons/hub`에 {PC 켜짐, 학생 화면 열림, 수업 제목 · 장면 수}를 써요. 창을 닫을 때는 ‘꺼짐’으로.
- 휴대폰 대기 화면은 이 세 가지를 보여 주고, 다 준비됐을 때만 ‘수업 시작’을 눌 수 있어요. 누르면 **확인 줄**(‘PC · 학생 화면 · 이 휴대폰에서 함께 시작해요’)에서 한 번 더.
- 실제 시작은 **교사 PC가** 해요: 휴대폰이 `hub.startReq`를 보내면 PC가 받아 수업을 시작(지금 ‘수업 시작’과 같은 동작) → 세 화면이 함께 시작. PC가 4초 안에 답하지 않으면 휴대폰은 ‘교사 PC가 응답하지 않아요’를 보여 주고 요청을 거둬요. PC는 10초 넘은 요청은 받지 않아요(끊겼다 이어진 뒤 뒤늦게 시작하지 않게).
- 학생 화면 창은 PC에서 사람이 눌러야 열려서(브라우저 규칙), 닫혀 있으면 휴대폰에서 시작하지 못하고 ‘PC에서 학생 화면을 먼저 열어 주세요’를 보여 줘요.
- 기존 진행 · 0.7 복구 · 끝내기는 그대로예요.

## 6. 실제 Firebase에 켜려면 (승인 필요, 아직 하지 않음)

PIN 4자리 연결은 Spark 무료 요금제 그대로, 서버 함수(Cloud Functions · Blaze) 없이 돼요. 필요한 것은 두 가지예요.

1. **Firebase 콘솔 → Authentication → 로그인 방법 → ‘익명’ 켜기** (무료). 익명 로그인만으로는 아무것도 못 읽어요. 규칙이 ‘교사 PC가 허용한 기기 문서’를 따로 봐요.
2. **보안 규칙 배포** (`firebase deploy --only firestore:rules --project navi-presenter-fd289`). 지금 실제 규칙보다 넓어지는 부분은 ‘허용된 휴대폰이 그 수업 · 수업 내용 · 설정 · PC 준비 상태를 읽고, 수업을 넘기고, 시작 요청을 남기는 것’과 ‘PIN 자리 문서(`pins`, 3차)’예요. 구글 교사 자리 규칙은 그대로예요.
3. 그다음 `public/navi-config.js`의 미리보기 설정에 `pin: true`를 더하면 PC ‘휴대폰 연결’ 창과 휴대폰 첫 화면에 ‘PIN 4자리로 연결’이 보여요.

`lessons/hub`(휴대폰에서 수업 시작)도 새 문서라 **2번 규칙 배포가 있어야 실제 미리보기에서 동작**해요. 배포 전 실제 미리보기에서는 휴대폰 대기 화면이 ‘PC 준비 기다리는 중’에 머물고(규칙이 막아서), PC에서 시작하는 기존 방법은 그대로 돼요.

남는 한계: PIN 자리 하나당 요청 3개라서, PIN을 바꿔 가며 열린 자리를 찾는 시도 자체는 규칙으로 막지 못해요(들어오지는 못해요: PC 허용이 필요). 실제로 켜기 전에 App Check(무료로 시작)를 더하는 것을 권해요(9-2 · 9-5).

| 4. 연결 코드 UX | 사용자에게는 **‘휴대폰 연결 코드 6자리’** 만 보여요(‘연결 코드로 연결’ · ‘연결 코드 만들기’). 4자리는 ‘QR 주소의 수업 번호 · 휴대폰에 넣는 번호가 아니에요’로 작게 바꾸고, 단추도 ‘QR 보기’ · ‘수업 번호 바꾸기’로 나눴어요. 6자리 코드 · run · 요청 id는 모두 `crypto.getRandomValues`로 만들어요(6자리는 치우치지 않게 나머지 범위를 버려요) |

## 9. 3차: 연결 번호를 PIN 4자리 하나로 (교사 검토 반영)

6자리 연결 코드를 없애고, 수업 PIN 4자리 하나로 PC와 휴대폰을 이어요. **PIN만 맞혀서는 아무것도 열리지 않는 구조**(요청 → 교사 PC 허용 → 그 수업 리모컨)와 2차의 보안(명령만 · PC가 검증 · 수업별 run · 기기 권한 만료)은 그대로예요.

### 9-1. 흐름

| 단계 | 누가 | 무엇을 |
| --- | --- | --- |
| 1 | 교사 PC | ‘휴대폰 연결’ 창(또는 발표 설정의 ‘QR 보기’)을 열면 그 PIN의 자리 `pins/{PIN}`을 **3분 동안** 맡아요: {교사, 수업 `s{PIN}`, lease(열 때마다 새 난수), 끝나는 시각, 열림, 요청 수 0}. 창을 닫거나 · 3분이 지나거나 · 한 대를 허용하면 닫혀요 |
| 2 | 휴대폰 | **QR로 열면** 주소에 PIN이 들어 있어서 ‘PIN 4자리로 연결’을 한 번 누르면 바로 요청해요. **QR 없이 열면** 네 칸에 넣어요(저절로 다음 칸 · 빈 칸에서 지우면 앞 칸 · 붙여넣기 · 자동 채우기). 익명 로그인 → `pins/{PIN}/asks/{휴대폰}`에 요청 하나(lease · 누른 시각 · ‘iPhone’ 같은 기기 종류만) |
| 3 | 교사 PC | 요청 줄 ‘iPhone · 연결 요청 · 방금’ → **허용 / 거절**. 요청이 둘 이상이면 ‘내 휴대폰이 아닌 요청은 거절해 주세요’ |
| 4 | 교사 PC | 허용하면 기기 문서(그 수업 · 이번 run · 3시간) + 요청에 답 + 자리 닫기를 한 번에 써요. 그다음은 2차와 같아요(휴대폰은 명령만 · PC가 검증해 적용 · 수업이 끝나면 run이 바뀌어 끝) |

### 9-2. 4자리라서 다시 본 위험과 막는 방법

6자리 설계를 숫자 길이만 줄이면 안 돼요. 4자리는 1만 가지뿐이고, 교실 화면에 보이고, 다른 교사도 같은 번호를 쓸 수 있어요. 그래서 PIN을 ‘열쇠’가 아니라 **교사가 잠깐 여는 문 번호**로만 쓰고, 열쇠는 교사 PC의 ‘허용’이 맡아요.

| 위험 | 막는 방법 |
| --- | --- |
| PIN 맞히기(1만 가지) | 맞혀도 요청 하나만 남길 수 있어요. 들어오려면 **교사 PC의 ‘허용’** 이 꼭 있어야 해요. 요청은 교사가 창을 연 동안(3분)만 · 자리마다 3개까지 · 휴대폰마다 하나만 받아요(규칙이 요청 수를 같은 쓰기에서 함께 올려야만 받아요). 한 대를 허용하면 그 자리는 바로 닫혀요 |
| 교실에서 PIN을 보고 다른 휴대폰이 요청 | PC가 요청마다 기기 종류와 시각을 보여 주고, 둘 이상이면 경고해요. 거절한 휴대폰은 그 자리에서 다시 요청하지 못해요(교사가 다시 열어야 해요) |
| 같은 PIN을 쓰는 다른 교사 | 한 PIN 자리는 **한 번에 한 교사만** 맡아요(규칙). 남이 맡고 있으면: 수업 전(PIN 휴대폰 없음)이면 PC가 새 PIN을 받아 PC · QR에 같은 새 번호를 보여 줘요. 수업 중이면 PIN을 바꾸지 않고 ‘같은 PIN을 다른 반이 잠깐 쓰고 있어요’ → 1–2분 뒤 ‘다시 열기’. 남의 자리는 닫혔거나 3분이 지났을 때만 맡을 수 있어요. PC는 거절을 받으면 그 자리를 한 번 읽어, **정말 다른 교사가 열어 둔 자리일 때만** PIN을 바꿔요(아니면 잠깐 뒤 한 번 더 열어요) |
| 다른 교사의 요청이 섞임 | 요청은 그 자리의 lease를 달고 와요. 교사는 **지금 lease의 요청만** 보고 답해요(앞서 그 PIN을 맡았던 교사의 요청은 규칙이 보여 주지 않아요). 허용은 맡은 교사 자기 이름 · 그 PIN의 수업으로만 돼요. 수업 문서는 교사마다 따로(`teachers/{교사}/…`)라 PIN이 같아도 섞이지 않아요 |
| 예전 QR 사진 | QR에 교사 표시(`?t=`, 교사 id의 SHA-256 앞 8자리)를 넣었어요. 그 PIN을 지금 다른 교사가 맡고 있으면 휴대폰은 요청하지 않고 ‘이 QR은 지금 열린 연결과 맞지 않아요’라고 말해요 |
| PC가 꺼져 자리를 못 닫음 | 3분이 지나면 저절로 끝나요(규칙이 끝나는 시각을 봐요). 이미 허용한 휴대폰은 2차의 run 확인으로 다음 수업에 못 들어와요 |
| 스크립트로 1만 가지를 다 시도 | 열린 자리가 없으면 아무것도 쓰이지 않고, 열린 자리에도 요청 3개뿐이라 들어오지는 못해요. 다만 **실패한 시도 횟수를 세는 것은 Firestore 규칙만으로는 할 수 없어요.** 실제로 켜기 전에 App Check를 더하는 것을 권해요(9-5) |

### 9-3. 화면

- PC ‘휴대폰 연결’ 창: 왼쪽은 QR 하나(구글 계정 · PIN 둘 다 이 QR로 시작), 오른쪽 ‘PIN 4자리로 연결’ 칸에 **휴대폰 연결 PIN** 하나와 상태 한 줄이에요.
  - 연결 기다리는 중 · 2:41 남음 / 허용을 기다려요 / 휴대폰을 연결했어요 · ‘한 대 더 연결’ / 연결 시간이 지났어요 · ‘다시 열기’ / 같은 PIN을 다른 반이 잠깐 쓰고 있어요 · ‘다시 열기’
  - 발표 설정 카드도 같은 PIN과 상태를 보여 줘요. ‘PIN 바꾸기’를 누르면 PIN으로 연결한 휴대폰은 다시 연결해요.
- 휴대폰: 방법 고르기(‘구글 계정으로 연결’ · ‘PIN 4자리로 연결’) → QR이면 한 번 누르기, 아니면 네 칸 → 상태마다 다른 화면이에요.
  - 허용 기다리는 중(같은 PIN을 크게 · 남은 시간 · 취소) / 연결됐어요 / 거절됨 / 시간 지남 / 연결 닫힘(PC가 다른 휴대폰을 허용했거나 창을 닫음)
  - 입력 화면의 안내: 열린 연결이 없어요 · 요청이 너무 많아요 · QR이 지금 연결과 맞지 않아요
- 6자리 연결 코드와 ‘수업 번호’라는 말은 모두 없앴어요. PC와 휴대폰에는 같은 4자리 하나만 보여요.
- PIN은 `crypto.getRandomValues`로 만들어요(0000–9999, 치우치지 않게 60000 이상은 버려요). lease도 같은 방식의 96비트 난수예요.
- 전 · 후 사진: `docs/review-ux/compare-pin4-*.jpg` (전 = `after/` 6자리, 후 = `pin4/`).

  - 네 칸 자동 넘김 · 지우기 · 붙여넣기 · 틀린 PIN · 취소 · 시간 지남 · 다시 열기.

- 지금 배포된 규칙(PR #4) 사본과 함께 쓰는 시험: PIN 연결이 보이지 않고, QR에 교사 표시도 없고, 기존 구글 연결 · PC 시작 · 휴대폰 넘기기가 그대로 돼요.
- 바뀐 단추 이름 때문에 고친 곳: ‘수업 번호 바꾸기’ → ‘PIN 바꾸기’(`tests/connect.spec.js` 1곳). 기대하는 동작은 그대로예요.
- 로컬 `npm run test:all`: **통과 218 · 실패 0 · 건너뜀 75**(기존 213 + 새 5: 규칙 3 · 화면 2). 첫 전체 실행에서 기존 시험 하나(`realtime` 양방향 넘기기)가 한 번 시간 초과로 실패했어요. 그 시험만 4번, 전체를 2번 다시 돌려 모두 통과했어요(부하가 클 때 3초 안에 못 보낸 누름을 버리는 기존 동작으로 보여요)

### 9-5. 실제로 켜려면 (아직 하지 않음, 승인 필요)

6절 순서 그대로예요: 익명 로그인 켜기 → 보안 규칙 배포(이번에는 `pairs` 대신 `pins`) → `navi-config.js`에 `pin: true`. 정리된 순서 · 확인 · 복구는 `docs/PREVIEW-PR5.md`에 있어요. 켜기 전에 **App Check**(무료로 시작할 수 있어요)를 더하면, 스크립트로 PIN을 훑는 시도를 Firebase가 먼저 걸러요. 이것도 실제 프로젝트 설정이라 승인을 받은 뒤에 해요.

## 10. 4차: 실서버 적용 전 PIN 보안 최종 점검 (2026-11-04)

기존 4자리 PIN UX와 ‘교사 PC 허용’ 구조는 그대로 두고, 규칙만 보완했어요. 근거는 Firebase 공식 문서예요.

### 10-1. 위험별 판단

| 위험 | 3차까지 | 판단 | 4차에서 한 것 · 남는 것 |
| --- | --- | --- | --- |
| **4자리 전체 탐색** | 로그인한(익명 포함) 누구나 `pins/{PIN}`을 하나씩 읽을 수 있어서, 1만 번 읽으면 지금 열린 자리를 찾을 수 있어요 | 찾아도 할 수 있는 것은 요청 하나 남기기예요. **교사 PC가 허용해야 들어와요.** 다만 1만 번 읽기는 무료 하루 읽기(5만)의 20%라, 되풀이하면 그날 한도가 바닥나 서비스가 멈출 수 있어요(Spark라 요금은 안 나와요) | 규칙으로는 막을 수 없어요(휴대폰이 lease를 읽어야 해서). 보이는 정보를 줄였어요(아래 UID). 남는 위험은 App Check로 줄여요(10-2) |
| **교사 UID 노출** | 공개 문서에 `teacher`(교사 id)가 그대로 있었어요 | 교사 id만으로 데이터를 열 수는 없지만, 누가 언제 연결을 여는지 이어 볼 수 있어요 | **교사 id를 빼고 SHA-256 해시(`owner`)만 둬요.** 규칙이 `hashing.sha256(request.auth.uid)`로 직접 계산해 맞춰 봐서 남의 해시로는 만들 수 없어요. 휴대폰은 허용된 뒤에만 자기 요청 문서에서 교사 id를 받아요. QR의 교사 표시(`?t=`)는 해시 앞 8자리예요 |
| **임의 PIN 선점** | 구글 계정이 있으면 누구나 빈 PIN 자리를 3분씩 잡을 수 있어요 | 들어오는 위험은 없어요. 그 PIN의 교사는 수업 전이면 PC가 새 PIN으로 옮기고, 수업 중이면 ‘잠시 뒤 다시 열기’예요(구글 연결은 그대로 돼요). 대량 선점은 하루 쓰기 한도(2만)에 먼저 걸려요 | 5차(11절)에서 **시범 교사 허용 목록**을 두었어요. 목록에 없는 구글 계정은 PIN 자리를 맡지 못해요 |
| **요청 3회 소진** | PIN을 아는 사람이 익명 계정 3개로 자리를 채우면, 교사가 다시 열어도 같은 계정으로 또 채울 수 있었어요 | 실제로 막혔던 방해예요 | **거절하면 그만큼 자리가 비어요**(거절 수 `no`). **거절된 익명 계정은 그 PIN에 다시 요청하지 못해요.** 한 번 열 때 받는 요청은 **20개까지**. 그래서 방해하려면 거절될 때마다 새 익명 계정이 필요해요(Firebase가 IP 하나당 시간에 100개로 막아요). 우리 앱은 거절되면 새 익명 계정으로 다시 요청해서, 실수로 거절한 내 휴대폰도 다시 들어올 수 있어요 |
| **익명 계정이 쌓임** | 고려 안 함 | 이 프로젝트는 Identity Platform 방식이라 Spark에서 하루 활성 사용자 3,000명 한도가 있어요. 익명 가입도 이 한도를 써요 | 익명 로그인을 켤 때 **익명 계정 자동 정리(30일)** 를 함께 켜요. 켜면 익명 로그인은 한도 · 요금 계산에서 빠져요(공식 문서) |

### 10-2. App Check: 막는 것과 못 막는 것

- 막는 것: 우리 웹앱이 아닌 곳(스크립트, 다른 사이트)에서 공개 API 키로 보내는 Firestore 요청. 강제 적용하면 토큰이 없는 요청은 거절돼요. Authentication(익명 가입 포함)도 보호할 수 있지만 아직 **미리보기(Preview) 기능**이에요.
- 못 막는 것: 진짜 브라우저에서 우리 앱을 쓰는 사람(교실 안 학생 포함), 로그인한 악의적 사용자, 규칙의 빈틈. 그래서 규칙이 1차 방어이고 App Check는 보조예요.
- 한계(Spark):
  - 웹은 reCAPTCHA Enterprise를 써요. 무료 평가는 **조직 전체에서 월 1만 건**이에요.
  - 넘으면 토큰을 받지 못해(fail closed), 강제 적용 중이면 **정상 교사 · 휴대폰도 막혀요.** 공격자가 페이지를 되풀이해 열어 이 한도를 쓰게 할 수도 있어요.
  - 점수 단계도 4개뿐이에요.
  - 로컬 · CI · 에뮬레이터에는 디버그 토큰이 필요해요.
  - 강제 적용은 켜고 최대 15분 뒤에 반영돼요.
- 판단: **이번 실기기 Preview 시험에는 필요 없어요.** 여러 교사가 쓰기 전에 ‘감시만(강제 안 함)’으로 먼저 켜고 지표를 본 뒤 정해요. 앱 쪽 작업(App Check SDK 초기화, 디버그 토큰)은 그때 따로 해요.

### 10-3. 교사가 정할 것

- 시범 기간에 **교사 계정 허용 목록**을 둘지: 두면 모르는 구글 계정은 PIN 자리를 잡지도, 자기 자리에 쓰기를 쏟아 한도를 쓰지도 못해요. 대신 새 교사가 쓰려면 목록에 더해야 해요.

## 11. 5차: 시범 운영 교사 허용 목록 (2026-11-04, 교사 결정)

시범 기간에는 교사 계정 하나(운영 Google 계정)만 PIN 4자리 연결을 쓸 수 있게 했어요.

| 무엇 | 어떻게 |
| --- | --- |
| 목록 | Firestore 문서 `allowed/{교사 UID}` 하나가 교사 한 명이에요. 실제 프로젝트에는 관리자(교사)가 콘솔에서만 더하고 빼요. 앱은 **자기 문서가 있는지만** 읽어요. 남의 문서 · 목록 보기 · 쓰기는 아무도 못 해요 |
| 적용되는 곳 | 보안 규칙의 `isTeacher()` = 구글 로그인 + 목록에 있음. PIN 자리 **만들기 · 다시 열기 · 닫기 · 거절 수**, 요청 **보기 · 허용 · 거절**, 휴대폰 **기기 문서 만들기**(허용) |
| 그대로인 것 | 구글 계정의 교사별 수업 접근(`teachers/{자기 UID}`의 수업 · 설정 · 준비 상태 · 기록)은 목록과 상관없이 예전 그대로예요. 이미 허용받은 익명 휴대폰의 그 수업 읽기 · 명령도 그대로예요 |
| 화면 | 목록에 없는 교사의 ‘휴대폰 연결’ 창에는 PIN 칸이 없고 ‘PIN 4자리 연결은 시범 운영 교사 계정에서만 켜져요. 이 계정은 구글 계정으로 연결해요’가 보여요. 목록이 바뀌면 다시 열지 않아도 곧바로 따라가요(창을 열 때 한 번 더 서버에 물어요) |
| 시험 | 규칙: 시험용 목록(교사 A · B)으로 같은 PIN 두 교사 시험을 그대로 하고, 목록에 없는 교사 C는 PIN 자리 만들기 · 닫기 · 거절 수 · 요청 보기 · 허용 · 기기 문서가 모두 거절되고 자기 수업은 그대로 써요. 목록 문서는 자기 것만 읽고, 누구도 쓰지 못해요. 화면: 목록에 없는 교사는 구글 연결만 · PIN 자리를 직접 만들어도 `permission-denied` · 목록에 더하면 곧바로 켜지고 빼면 꺼져요 |
| 결과 | 로컬 `npm run test:all`: **통과 222 · 실패 0 · 건너뜀 75**(4차 220 + 새 2: 규칙 1 · 화면 1) |

### 11-1. 이 목록이 막지 **못하는** 것 (제한 사항)

- **익명 계정의 PIN 자리 읽기**: 로그인한 누구나(익명 포함) `pins/{PIN}`을 하나씩 읽을 수 있어요. 4자리 1만 개를 모두 읽어 지금 열린 자리를 찾는 것은 목록과 상관없이 돼요. 찾아도 요청 하나만 남길 수 있고, 들어오려면 교사 PC의 허용이 있어야 해요.
- **무료 사용량 남용**: 읽기 · 요청 쓰기를 되풀이해 Spark 무료 하루 한도(읽기 5만 · 쓰기 2만)를 바닥내면 그날 서비스가 멈출 수 있어요. 구글 계정은 목록과 상관없이 자기 자리(`teachers/{자기 UID}`)에 쓸 수 있어서, 목록으로 이것까지 막지는 못해요. Spark라 요금은 나오지 않아요.
- 이번 소규모 시험에서는 **App Check를 강제하지 않아요**(10-2). 위 두 위험은 시험 기간의 제한 사항으로 남겨요. 시험 뒤 Firebase 콘솔의 사용량을 확인해요.
